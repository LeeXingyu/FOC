# 3. 技术债清单

## 当前仍值得收口的点

- `mc_tasks.c` 中仍存在旧式分发痕迹，后续最好把高频路径进一步收敛到统一控制主线。
- `Axis_State_Machine()` 目前为空，建议明确它是否继续保留为扩展入口，还是直接并入任务调度。
- `mc_interface.c` 里有若干空实现函数，建议补上最小可用行为，或者明确标注为 `TODO` 并给出原因。
- `motor_control.c` 仍然强依赖全局 `g_axis`，短期无妨，但长期会影响模块独立性。
- `speed_autotune.c` 和 `curr_autotune.c` 的状态机较长，最好补一份“状态 -> 事件 -> 转移”的文档。
- 一些历史命名和 SG 命名仍有混合痕迹，未来最好统一风格，避免同一含义多个名字并存。

## 接口层面

- 对外 API 中有些函数名保留了旧语义，但内部实际实现已经更新，建议同步整理注释。
- 某些控制函数返回值语义较弱，长期建议统一错误码设计。
- 部分调试行为仍然直接写入控制状态，后续可考虑增加一层更明确的命令分发。

## 可维护性

- 建议为整定参数单独整理一个“默认值 + 推荐范围 + 适用电机类型”的表。
- 建议把硬件相关、控制相关、整定相关的头文件依赖再压一层，避免循环依赖回潮。
- 建议给 `speed_autotune.c` 和 `curr_autotune.c` 增加更明确的阶段注释，方便后续复核。

## 低优先级，但值得记账

- 注释存在部分编码显示问题，影响阅读体验，但不影响功能。
- 代码中仍有不少调试输出和临时调参痕迹，建议后续统一加开关。
- 某些空白分支和冗余变量会增加后续误读概率，建议逐步清理。
